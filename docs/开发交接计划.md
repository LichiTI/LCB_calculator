## 1. 已确认的需求

- 数据来自本地游戏资源；中文展示默认使用 `LLC_zh-CN`。支持切换 `ST` 等翻译包。
- 只提供同步化阶段 IV（四破）的有效数据。人格等级仍需单独设置，不能把四破当作满级。
- 同时提供标准六技能轮伤与多回合伤害 / DOT 模拟。
- 能查看技能整段描述、逐硬币效果、战斗被动、支援被动、Buff 名称及完整说明。
- 技能组分为基础技能区与追击区。
- 每个技能可以配置基础威力、总变动值、总增伤、总追伤；独立硬币变动值与独立硬币增伤以数组保存。

- 配置保存在 JSON 中，可命名、复制、导入、导出和复用。
- DOT 单独配置、单独列出结果。逐硬币保存泛型状态映射：稳定状态 ID → `{ potency, count }`，并提供带构造器的值类。
- 追伤类型暂按“固定值与比例都支持”设计，属于可调整的设计默认值。

## 3. 产品结构

推荐做本地运行的网页应用。资料提取在构建/导入阶段完成，浏览器读取标准化数据包；日常计算不依赖启动游戏或访问 Wiki。

页面分为四个区域：

- 人格资料：搜索、罪人/关键词筛选、固定四破、等级、翻译选择、技能及被动资料卡。
- 技能组配置：基础技能区、追击区、技能级修正、逐硬币数组表格、保存与导入 JSON。
- 场景配置：敌方数值、双方状态、支援被动、队伍条件、行动顺序、回合数与随机模式。
- 结果：直接伤害、追加伤害、状态伤害、每回合/累计曲线、状态变化、逐事件解释和覆盖情况。

DOT 在技能编辑器中占独立列，在结果中占独立区。按异常名称与回合列出施加记录、触发次数、实际 HP 伤害、理智伤害和结束时剩余强度/层数；名称随翻译包切换。总 HP 伤害只累计实际 HP 伤害，保留与直伤/追伤的分项，不重复计入 DOT。

点击或悬停状态词可以看说明，点击后能固定详情卡，兼容触屏。描述中保留使用时、战斗开始时、命中时、正反面命中时等作用时点。

## 4. JSON 配置契约

配套文件为 `calculator-presets.example.json`，JSON 本身不含注释。它是尚未绑定数值数据版本的模板，不能直接宣称能够算出真实伤害。

### 4.1 技能修正字段

| 字段 | 界面名称 | 含义 |
| --- | --- | --- |
| `basePower` | 技能基础威力 | `null` 读取游戏有效基础值；数值表示覆盖基础值，0 是有效覆盖值 |
| `totalCoinPowerDelta` | 总变动值 | 对每枚硬币追加的统一威力变动修正，可正可负 |
| `coinPowerDeltas` | 独立硬币变动值 | 第 i 项对应第 i 枚逻辑硬币的额外修正 |
| `totalDamageBonusPct` | 总增伤 | 添加到指定手动百分比增伤区间的统一修正；20 表示 20%，不是 0.2 |
| `coinDamageBonusPcts` | 独立硬币增伤 | 第 i 枚硬币在相同手动增伤区间中的额外百分比 |
| `totalExtraDamage` | 总追伤 | 统一追加伤害配置，支持固定值、比例、计算基数、结算时点、修正规则 |
| `coinDots` | 独立硬币 DOT | 数组第 i 项为第 i 枚逻辑硬币的额外状态施加映射：状态 ID → `{ potency, count }` |

手动硬币修正示意：

```text
该硬币的有效威力变动
  = 游戏数据与已触发效果计算出的该硬币威力变动
    + totalCoinPowerDelta
    + coinPowerDeltas[i]

该硬币的手动百分比增伤输入
  = totalDamageBonusPct + coinDamageBonusPcts[i]
```

上述第二式只定义手动修正如何汇合，游戏原有的不同增伤区间、独立乘区和结算阶段仍按原机制处理。禁止把游戏全部增伤平铺到一个总百分比。

数组规则：缺省数组可由编辑器按当前硬币数初始化为全 0；保存为确定配置后，数组长度必须与逻辑硬币数相同。导入时不静默截断、循环或补齐不匹配的数组。重新使用同一硬币引用同一个逻辑索引；新增硬币/变体技能按其独立数据映射。负硬币保留符号，不以绝对值代替。

### 4.2 追击区与总追伤

- 基础技能区保存技能引用、每轮次数与修正参数。
- 追击区保存独立的技能执行项：触发源、触发事件、概率、目标、次数限制、技能引用及自己的修正参数。
- 总追伤是某次已结算伤害的附加伤害事件；追击区执行项会产生自己的技能/硬币流程。日志分别标明两类事件。
- 追伤默认绑定每枚成功命中的硬币。也可设为技能完成一次，此时比例基数为该技能符合条件的命中伤害之和；固定值只加一次。
- `resolvedHitDamage` 指命中经攻击伤害公式与舍入后、吸收护盾与剩余 HP 截断前的值；`actualHpLost` 指本次直接命中实际扣掉的 HP。比例追伤必须选择基数，不使用含自身追伤的总伤害递归计算。
- `fixedDamage` 的单位为 HP；`ratioPct` 的单位为百分比。两者形成追加事件的过程以及舍入位置由明确的追伤规则处理。
- `modifierPolicy` 区分固定追加、按指定罪孽抗性处理、复用特定规则等。默认手动固定追伤不再次应用普通攻击增伤；真实游戏追加伤害以对应效果的专用处理器为准。
- 默认手动追伤不再触发命中效果；真实游戏需要二次触发的特殊效果单独声明。
- 追击按技能动作 ID 计数，不消耗基础技能区的六技能次数。需要消费牌、资源、行动槽的特殊追击必须显式配置其消费规则。
- 默认不允许追击产生无限追击链，设置每动作触发上限和链深限制。达到保护上限时报告不完整结果，不能把截断值当完整伤害。

### 4.3 保存内容与来源

JSON 保存技能组、人工修正、场景和随机种子；数据包单独保存已解析游戏数据与翻译。配置必须引用 `dataVersion`、`rulesVersion` 和格式版本，便于下次复现。

手动修正属于叠加层；输入前显示“游戏基础值 / 自动触发修正 / 手动修正 / 当前结果”。`basePower` 覆盖原始基础值后，仍计算有效的自动威力修正。如果需要覆盖某个自动效果，按 effect ID 显式关闭，避免既自动算一遍又手动加一遍。自动追击与人工追击也按来源 ID 去重；替换与额外添加必须是不同操作。

导入后保留未知状态或技能 ID 并报告错误，不删除内容。升级 JSON 格式提供迁移函数，旧版本数据缺失时标明不可复现。展示语言切换不改变任何计算结果。

### 4.4 DOT 的泛型值与逐硬币配置

采用具名字段 `{ potency: number, count: number }` 表示用户提出的二元值。键保存稳定游戏状态 ID，界面显示正式中文或所选翻译；切换翻译不需要改 JSON 键。`dot-types.ts` 提供可复用的 `StatusAmount` 类、构造器、JSON 转换与泛型映射类型。

```ts
type DotMap<K extends string = string> =
  Partial<Record<K, { potency: number; count: number }>>;

type CoinDots<K extends string = string> = DotMap<K>[];
```

下例仅演示三个硬币的配置格式，不代表任何真实技能：

```json
{
  "coinDots": [
    { "Combustion": { "potency": 3, "count": 1 } },
    {
      "Combustion": { "potency": 0, "count": 2 },
      "Laceration": { "potency": 2, "count": 0 }
    },
    {}
  ]
}
```

- `coinDots[i]` 是本次该硬币效果额外施加的量；目标当前持有的状态保存在运行时状态中。配置值对象不直接充当共享的可变战斗状态。
- 当前预设中的 `coinDots` 是手动叠加层，默认在该硬币成功命中后的手动效果阶段向当前目标施加一次；其优先级由引擎明确规定。空映射表示没有手动追加，游戏原有 DOT 效果仍由原始规则执行。不可把原始效果再复制到手动配置里重复计算。
- 真实游戏效果的正/反面条件、暴击条件、目标、优先级、本回合/下回合生效、动态强度等，继续由该硬币的效果规则持有。仅触发事件、目标、条件、作用时点均相同且允许合并的施加操作可以汇总到一个映射；有先后关系的操作必须分别执行。
- 同一硬币可施加多个不同异常。相同异常若有多个不同条件或时点，分别保存在效果操作中，不能用同一个对象键覆盖此前的操作。
- `potency=0, count>0` 和 `potency>0, count=0` 均为有效施加量；`0,0` 为无操作。无现存状态时如何建立初始层数、达到上限如何处理，由对应游戏状态规则决定，构造器不擅自补 1。
- 值类只检查非负安全整数，不统一写死 99 等游戏上限。削减、清除、消耗、转换属于独立状态操作，不把它们塞进本次非负施加量。
- `coinDots.length` 与其他逐硬币数组相同。旧版预设缺少此字段时可初始化为每币一个独立的空对象；显式提供了错误长度则报错。不能用 `Array(n).fill({})` 共享可变对象。
- JSON 保存普通对象。若调用方需要类实例，使用 `StatusAmount.fromJSON` 校验并恢复；仅 `JSON.parse` 不会恢复构造器和方法。
- 技能级、被动或回合事件施加的异常也复用相同值结构，仍挂在各自事件上。DOT 伤害何时触发、消耗多少层数，由状态处理器负责，不能统一按每枚硬币立即造成 `potency × count` 的伤害。
- `reporting.separateDotDamage` 控制独立 DOT 结果区，`dotBreakdownBy` 默认按状态 ID 与回合汇总。实际伤害归属沿用事件日志规则，施加量不冒充已造成的伤害。

## 5. 两种计算模式的准确口径

### 5.1 标准轮伤

标准基础技能池为 3×S1、2×S2、1×S3，但次数保留为配置项，特殊替换或额外技能按实际规则处理。

提供两个明确的子模式：

1. **静态对比**：每次使用技能前恢复相同初始场景，按 3/2/1 次数加权求和；适合横向比较。结果标签写明“状态重置的六技能加权伤害”。跨回合 DOT 不自动混入该指标。
2. **连续轮转**：按用户排列的六次技能行动执行，状态与资源连续传递，并把行动放入明确的回合/行动槽。计算本轮内实际发生的直接伤害、追伤和 DOT。

六次技能行动不默认等于六回合。默认模板可以采用每回合一个行动，但必须展示这一假设。`initialStatePolicy: byMode` 由模式决定：静态对比在每次技能前重置，连续轮转和多回合保留跨动作状态。轮转结束时残留的状态单独显示，不把全部未来 DOT 提前算入本轮。可选“继续结算到清空”时明确延长的回合窗口与敌方动作。

### 5.2 多回合模拟

- 指定回合数、我方技能顺序、速度或行动顺序、行动槽、初始状态与资源。
- 指定敌方攻击硬币事件、拼点过程或经过验证的拼点脚本、是否具有理智值、部位等。
- 早期版本以手动动作脚本完成完整事件结算；后续加入真实抽牌、技能保留/弃牌/替换、洗牌及拼点算法。脚本模式结果明确依赖给定动作。
- 敌方动作缺失时，不假设流血会自行每回合结算。已知无法确定的部分报告为待定，不用 0 冒充准确结果。
- 遭遇有限 HP 目标时正确处理死亡、取消后续动作与过量伤害；无限 HP 木桩作为独立场景模式展示。

### 5.3 随机与条件

- 支持固定正反面/暴击序列；“全正面”只是一个场景，不是所有人格的伤害上限。
- 小状态空间可以精确枚举，状态复杂时使用带种子的 Monte Carlo，并显示样本数、均值、标准误或置信区间。
- 概率计算必须实际经过状态分支。不能先把正面数量取平均再套条件技能、暴击和 DOT 公式。
- 理智、状态、暴击、速度与抽牌可能彼此影响；随机试验保留相关状态，不能把每枚硬币独立计算后随意相加。
- 样本最小/最大值标注为观测值；没有穷举证明时不称为理论上下限。

## 6. 计算引擎与机制覆盖

采用独立于 UI 的事件引擎。同一个状态序列和随机流应得到相同结果，支持保存日志回放。

事件类型至少区分：回合开始、战斗开始、选择动作、使用技能、拼点、掷硬币、命中前、直接命中结算、命中后、暴击、追伤、追击、技能结束、死亡/击杀、回合结束。这个列表是需要建模的事件类别，实际先后顺序和同阶段优先级必须按游戏实现确认。

每条效果包含触发事件、优先级、条件读取时点、目标选择、修改操作、生效期限、次数上限、来源和可验证证据。自然语言翻译只负责呈现，计算运行时不调用 LLM 解读文本。

### 6.1 伤害及场景因素

- 基础威力、加减/特殊硬币、硬币复用/追加/销毁、攻击权重、技能变体与额外动作。
- 人格等级、攻击等级与防御等级、攻击类型/罪孽抗性、基础威力/硬币威力/最终威力修正。
- 增伤减伤、易伤、保护、暴击、固定伤害、按已造成伤害追加、伤害上限与各阶段舍入。
- 速度差、HP 阈值、理智变化、混乱与混乱阶段、护盾、部位及死亡导致的中途条件变化。
- 战斗被动、支援被动、罪孽资源持有/共鸣条件、目标选择和队伍限制。被动的检查时点、目标锁定/重选时点不能统一猜测。
- 同一罪人的出场人格与支援人格关系按阵容规则校验；不能无条件勾选所有被动同时生效。

### 6.2 状态与资源

| 类别 | 需要实现的关键行为 |
| --- | --- |
| 烧伤 | 回合结束触发、强度与层数变化、附加引爆或专属变体 |
| 流血 | 攻击硬币掷出时的伤害及层数消耗；与拼点/动作时间线配合 |
| 破裂 | 对应命中事件触发、层数消耗、施加与消耗的准确时序 |
| 沉沦 | 有理智/无理智目标分支，理智伤害与 HP 伤害分账，泛滥等专属机制 |
| 震颤 | 普通震颤对混乱阈值的影响、引爆、转换/叠加及造成 HP 伤害的特殊版本 |
| 呼吸法 | 暴击概率、触发/回合结束时的资源消耗、暴击关联效果 |
| 充能及其他人格资源 | 获取、消耗、上限、保留、跨技能状态、形态转换 |
| 常见 Buff/Debuff | 威力、硬币威力、增伤减伤、速度、攻防等级、保护/易伤及其有效期 |
| 专属机制 | 按人格真实引用发现，例如弹药、弃牌、特殊标记、额外技能、特殊硬币、场外支援等 |

状态实例至少记录 ID、拥有者/部位、来源、强度、层数、上限、施加回合、当前/下回合生效、过期条件与内部资源。不同状态可能只有层数或额外计量，不强制所有状态套同一种递减方式。

在玩家界面可统称 DOT/状态伤害，但统计分开列出 HP 伤害、理智伤害和混乱阈值变化。支援者施加状态、主攻者触发状态时，团队伤害只计一次；默认按触发事件归属，施加贡献作为单独说明。

### 6.3 完整性要求

静态资源可能仅保存 `scriptName`、效果代码或条件参数，完整算法仍在游戏程序中。必须建立“效果 ID → 已验证处理器”的映射，必要时对照本地程序、元数据和可复现游戏记录。

未知效果保留原文并标注“仅展示 / 部分实现 / 已验证”。凡会影响该场景结果的未知效果，结果必须显著显示覆盖缺口；不能默默忽略后输出“精确总伤害”。

## 7. 数据导入与文本展示

执行顺序：

1. 保存只读源快照清单，包括游戏构建线索、当前目录哈希、每个输入文件哈希和时间。
2. 解析当前 Addressables 目录，定位依赖的缓存 `__data`/资源包，提取需要的 TextAsset/ScriptableObject。先对一组人格验证再批量处理；资源缺失报告缺项。
3. 导入人格、技能、逐硬币参数、被动、Buff、成长/等级配置、合法技能池和转换关系。
4. 解析四破有效数据。保留原始 ID、资源地址、JSON 路径和原始版本，支持审计。
5. 以类型+ID+有效阶段建立文本连接；按当前实际加载清单和覆盖规则处理补丁文件。不能按文件名排序后“最后一项胜出”。
6. 默认展示 `LLC_zh-CN`。缺译回退到用户配置的原语言，例如英文，并标记缺译；`ST` 是独立可选翻译包，不能作为正式中文的静默补全来源。
7. 用受控富文本解析器处理 `<color>`、`<u>`、图标、技能标签和 `{0}` 参数。保留换行、作用对象和时点；未知标签显示可诊断占位，不直接执行任意 HTML。
8. 输出人格清单、字段缺失、重复 ID、悬空引用、文本缺失、四破解析、未知规则与版本冲突报告。

游戏目录及缓存均只读，提取结果放在独立项目中。排除 `_grad_backup`、`_fixwork`、工作临时文件及未被当前资源引用的 nextupdate 文本。是否为可用人格由当前游戏数据判定，不能把所有翻译条目都加入列表。

## 10. 验证与验收清单

重要的是独立参考结果，而不是用同一公式生成期望值来测试自身。

- 四破选择：1/2/4 稀疏版本、缺失四破、变体技能、被动解锁、补丁覆盖。
- JSON：0 与 null 的区分、负硬币、数组长度、百分比单位、未知 ID、版本迁移、保存往返。
- 统一修正：每枚硬币恰好应用一次总变动值和自己的修正；重用硬币不会把全技能增益重复累计。
- 追加效果：固定/比例、每币/每技能、护盾与残血基数、追击触发上限、来源归属、递归保护。
- 状态：先施加/先消耗的边界、层数归零、强度为零、达到上限、下回合生效、回合末同时到期。
- DOT 配置：单币多异常、纯强度/纯层数、空映射、数组长度、独立对象、JSON 往返、同异常不同事件不丢失、自动与手动施加不重复。
- 场景：敌人不行动时流血、有/无理智的沉沦、震颤阈值变化与 HP 伤害分离、状态施加与触发来自不同角色。
- 随机：固定种子重放、小案例精确枚举对照 Monte Carlo、正反面与条件变化的关联。
- 顺序：调整 S1/S2/S3 顺序会影响相关资源；静态重置模式与连续轮转模式不能混淆。
- 死亡与部位：残血截断、过量伤害、护盾、混乱中途发生、目标消失导致后续事件取消。
- 被动：满足/不满足资源阈值、目标选择边界、支援关系、条件检查时点和自动/手动修正去重。
- 翻译：正式中文缺译回退、ST 切换、带格式的技能标签、占位符和 Buff ID 链接。
- 每条结果能追溯“第几回合 → 谁使用哪个技能 → 第几枚硬币 → 哪项效果 → 状态前后值 → 伤害构成”。

最终交付必须包括可启动程序、数据导入流程、可复用 JSON、规则覆盖报告和已知缺口。对照数值未通过的效果不能标记“已验证”。

## 12. 实现状态（2026-10-30 追加）

本节的条目均已在 `calculator/` 内实现并通过 `tsc -b`、`vitest run`、`npm run build`。

### 12.1 排轴与轮伤呈现

- **手动排轴器**（`src/ui/ScheduleEditor.tsx`）：按回合列出动作，支持增删回合、增删动作、按技能组自动填充；写回 `preset.simulation.actionSchedule` 并切换 `orderedCycle`，与穷举结果格式一致。
- **守备动作参与结算**（`src/engine/simulator.ts`）：`defType` 为 `GUARD`/`EVADE` 的技能不再被直接跳过，而是照常结算「使用时 / 技能结束」脚本。因此把反击（`1061704`）、援护防御（`1061705`）排进行动表后，「听讲准备 → 听讲时间 → 易伤 + 强化失误技能」的链条会自动接上；当行动表已显式安排 `SupportiveDefense` 时，回合末的援护防御补偿不再重复触发。
- **轮伤精算表**（`src/engine/rotation-table.ts` + `src/ui/RotationDamageTable.tsx`）：把事件日志折叠成「一行一次出招 / 一个状态变体」的表格——硬币点数序列、点数合计、第一乘区（`(Δ+25+Δ)/(|Δ|+25)` 与抗性/暴击项）、增伤倍率、单次伤害、权重（默认等于出现次数，可填 0.5 的倍数折算双槽与跨轮均摊）、合计；底部给出 `直伤：11×3 + 20×2 + 30 = 103 + DOT 13 = 轮伤 116` 的一行式汇总与「复制为纯文本」。
- **敌方 DOT 收支**：`SimulationResult.dotBalance` 汇总每个状态的初始量、施加、消耗、净层数与结束值，并给出「净增 / 刚好打平 / 净减 / 会掉光」结论。

### 12.2 暴击与重投

- **全暴击开关**：`preset.actor.forceFullCrit`（界面「按全暴击结算（呼吸法满暴）」）强制每枚硬币暴击；呼吸法 20 强度本身即 100% 暴击，两者结果一致（测试已固定该等价性）。
- **暴击加伤家族**：`CriticalDmgUpByRatio<N>`、`CriticalDmgUpByJsonValue`、`CriticalDmgUpByBuffStack(IfAlly)`、`CriticalDmgUpByRatioOn{CriticalActivated,StartTurn}ViaBuffCheckDevideByStackWithLimit<N>`、`CriticalDmgUpOnSCViaSelfBreathAndBuffDivide`、`CriticalDmgUpByBreathStackAndTurnLimit40`、`FullStopHongluCriticalAttackDmgUpByRatio`、`BrokenUnitCriticalDmgUpByJsonValue` 均按技能级快照或逐硬币实时两条路径计入。
- **硬币重投家族**：`getCoinScriptRerollLimit` / `getActiveCoinRerollLimit` 覆盖 `Reroll(Via|OnSA|OnSAH)…Upto1/2/3/5`、`RerollOnSuccessCriticalAttackHead`、速度与充能条件重投、`RerollCoinByValue`、`RerollOnSAViaConditionalBuffCheckAndUseResult*` 等；重投次数不再固定为 1 次。

### 12.3 吃满所需的敌方状态

- `inferRequiredStatusesForIdentity(core, identityId)`（`src/engine/bonus-tier.ts`）只统计「按状态缩放威力/伤害/暴击」的脚本（`CoinScaleAdder*` / `SkillPowerResultAdder*` / `AttackDmgUp*` / `CriticalDmgUp*` 等），推导吃满所需的最低强度与层数；纯施加类脚本（`GiveBuffOnSucceedAttack` 等）不会被误判成需求。
